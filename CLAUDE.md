# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

`wandb-cli-tool` is a keyboard-driven TUI, read-only except for explicit user-triggered edits (a run's group, tags and name; copying a run; stopping and deleting runs), for browsing Weights & Biases (SaaS, not self-hosted) projects, runs, charts, tables, and media. The user types one command and navigates with arrow keys, Enter, and Esc. Currently implemented: login/logout/change entity, project and run lists, a run screen (tags and machine/git/command info on top; menu: Logs, Charts, Config tree, Files), comparing runs, charts in panels with plot options, run filter / bulk actions / state-change notifications, followed live logs, setting a run's group, adding tags, renaming, copying, stopping and deleting runs, and previewing image/audio files. Tables and artifacts are later phases.

## Commands

```
uv sync                                   # create/update .venv
uv run wandb-cli-tool                     # launch the TUI
uv run pytest                             # all tests, in parallel on every core (~30 s; serial was ~9 min)
uv run pytest -n0 tests/test_pins.py      # serial: for a debugger, `-s` output, or when timing matters
uv run pytest tests/test_app.py::test_logout_clears_credentials_and_shows_login   # one test
uv tool install .                         # put `wandb-cli-tool` on PATH
```

## Architecture

- `api/` is the only package that imports `wandb` (`client.py`, plus `copy_run.py` whose adapters run only in a child process). It defines the `WandbClient` protocol (entities, projects, runs, console lines, metric keys, metric series, system rows) and the real `WandbApiClient`. Screens use `app.client`, never `wandb` directly. Keep it read-only.
- `app.py` (`WandbCliApp`) owns auth state and the screen stack. It takes a `client_factory(api_key)` so tests inject a fake. `_start(creds)` enters the logged-in state by resetting the stack to `ProjectsScreen`. Logout and change-entity both go through it or `_reset_stack`. `check_action` hides entity/logout actions while logged out. Global keys: `q` quit, `e` change entity, `l` logout (they work on every screen but are `show=False` at app level; only `ProjectsScreen` lists them, via its own bindings, to keep the key bar short).
- `config.py` stores `{api_key, entity}` as JSON in the platformdirs config dir (mode 0600). Setting `WANDB_CLI_TOOL_CONFIG_DIR` overrides the dir. Tests rely on this via an autouse fixture, so they never touch the real config.
- `screens/browse.py` (`BrowseScreen`) is the shared base for list screens, a `DataTable` (one column per `columns` entry). A `@work(thread=True, exclusive=True)` worker iterates `fetch()` and appends rows in batches via `call_from_thread`, so long run lists stream in; duplicate keys are dropped (live data can shift between pages). Subclasses (`ProjectsScreen`, `RunsScreen`) implement `fetch()`, `open_item()`, and optionally `render_cells()` for styling.
- List rows are `Item(key, cells, meta)`: `cells` are plain strings (JSON-cacheable), `key` is the row key (e.g. run id), `meta` is a hidden payload. Cached rows whose cell count no longer matches `columns` are ignored. Run flow: `ProjectsScreen` → `RunsScreen` → `RunScreen` (menu) → `LogsScreen` / `ChartsScreen`.
- `charts.py` and `series.py` are UI-free logic: panel grouping (`metric.split("/")[0]` is the panel, no `/` goes to "Other", "System" is always first), `ChartSpec(y, x, system)`, x-axis options, and row → point extraction. Keep logic there so it is testable without Textual.
- Chart kinds (`ChartSpec.kind`): **plot** (`y` + `more` = 1-8 series on one shared x-axis; all run metrics or all system metrics), **bar** (`y` + `more` = metrics shown as horizontal bars in the user's order, each bar the latest value: summary for run metrics, last reading for system metrics), **table** (`y` = key of a `wandb.Table`). Adding a chart is two steps: `ChartKindDialog`, then `PlotDialog` / `BarDialog` / `TableDialog` (`screens/chart_dialogs.py`; `MetricPicker` is a filterable multi-select that records pick order; bars are reordered with Ctrl+↑/↓ in the dialog's order list). Widgets are in `screens/chart_widgets.py` (`ChartView` plotext, `BarView` custom Rich, `TableView` DataTable, all `ChartBase`, found via the `chart-widget` CSS class); `x` only applies to plots; Tab/Shift+Tab cycle focus panel list -> charts (the way out of a table, where arrows move the cell cursor). UI-free logic: `palette.py`, `barchart.py` (`layout_bars`), `tables.py`. Saved layouts from before kinds existed still load (missing `kind`/`more` = plain plot).
- Colors follow the dataviz skill's reference palette (`palette.py`), unchanged: fixed slot order, never cycled (hence max 8 series), a series' color is its position in the chart (a series with no data keeps its slot), legend whenever there are 2+ series, one hue for all bars, text (names/figures) in the text color. Dark vs light values are chosen from the Textual theme. The skill's `validate_palette.js` could not be run (no node here); the palette is used as documented, which the skill records as passing its adjacent-pair checks.
- Periodic refresh (`ChartsScreen`, `refresh.py`): `_fetch_data()` (one `ChartData` bundle incl. the run's state) is shared by the first load and every refresh. A refresh (key `r`, or the timer) rebuilds the *default* layout from the new metrics under the same `custom`, then updates charts **in place** if the shown panel's specs are unchanged (keeps focus/scroll/table cursor) or remounts the panel keeping the focused index. Failures while refreshing are `quiet`: the old data stays and only the status line reports it. The timer exists only while the run is `running` and an interval is chosen (`f` cycles; saved as `chart_refresh_seconds`, default 30 s), stops itself when the run finishes, and ticks are skipped while a dialog is open or a refresh is in flight. Finished runs are never refreshed automatically.
- Image charts (`ChartSpec.kind == IMAGE`; `images.py`, `ImageChartView`/`StepSlider` in `chart_widgets.py`): keys come from summary entries with `_type` `image-file` / `images/separated`; the steps come from `scan_history(keys=[key])` (bounded, sampled evenly to 1,000 steps keeping first and last). The view posts a debounced `Wanted` message when its (step, image) changes; `ChartsScreen` downloads the file (content-addressed under the files cache, size-capped), makes a screen-sized thumbnail in the worker thread (`make_thumbnail`; decoding a 20 MB PNG on the UI thread each draw was ~0.75 s) and calls `show_image(path, token)`; a response whose token is no longer wanted is dropped, so a slow download for a step you left never overwrites the current one. On refresh the slider keeps its step, or follows the newest if it was at the end.
- Tables: a run's logged `wandb.Table`s come from the summary entries with `_type == "table-file"` (`tables.table_entries`); `table_data` downloads the `.table.json` (path-checked, 20 MB cap, 1,000 rows / 60 columns shown) and `parse_table` formats cells (media cells become `[image] name`). Only the latest version of each key is shown; tables logged inside artifacts are not.
- **Textual attribute-name collisions have bitten twice:** never name your own widget/screen attributes `layout` (read-only Textual property; use `chart_layout`) or `loading` (Textual shows a spinner overlay and makes the widget unfocusable; use `waiting`). Also never override `on_mount` in a subclass and call `super().on_mount()`: Textual already runs `on_mount` of every class in the hierarchy, so the base would run twice (use the `BrowseScreen.prepare()` hook).
- **Never pass untrusted text to Textual as a plain `str`.** Textual parses `str` content as markup: `run [v2]` loses `[v2]` and a stray `[/x]` raises MarkupError and crashes the whole app (Static, Label, Select, OptionList, SelectionList, `border_title`, DataTable cells). Names, tags, groups, metric names, table cells and server error messages are arbitrary text, so wrap them with `plain(...)` (Rich `Text`) or `plain_title(...)` (`Content`, for border titles), or use `markup=False` on Static/Label. `WandbCliApp.notify` already forces `markup=False`. `tests/test_plain_text.py` feeds hostile strings through every screen.
- Metric names come from the run's *summary* (numeric values only). Default x is `_step`. System metrics come from the separate system stream (`history(stream="system")`), loaded once per `ChartsScreen`, and plot against `_runtime`/`_timestamp`. Panel/chart customizations are persisted per **project** (`layout_store.project_key(entity, project)`, stored under `"projects"` in `chart_layouts.json`; `LAYOUT_VERSION` 2 — version-1 per-run files are ignored on purpose), so every run of a project shows the same customizations on top of defaults generated from that run's OWN metrics: `charts.py` holds `Customization` (only what the user changed: created panels, added charts, x-axis overrides keyed by `chart_key`, never positions) and `ChartLayout` (default panels + customizations; every edit goes through its `add_panel`/`add_chart`/`set_chart`/`reset`). Customizations are re-applied on top of a freshly built default each time, so metrics logged later still appear. `layout_store.py` (`LayoutStore`) writes them to `chart_layouts.json` in the config dir (not the cache, so logout/cache clears keep them), immediately after each change, atomically, never raising; files with another `LAYOUT_VERSION` or that are unreadable are ignored and overwritten, so **bump `LAYOUT_VERSION` in `charts.py` whenever the stored format changes** (settings may be dropped during development). `d` in `ChartsScreen` resets to the default after a yes/no confirmation. Deleting a chart (`Delete`/`Backspace` on a focused chart, with confirmation) goes through `ChartLayout.remove_chart`: an added chart is dropped; a *generated* chart is recorded in `Customization.removed` by `chart_key` (not index, so new metrics don't shift it) and hidden by `apply_customization`. A chart's index in a panel is its index among the non-removed generated charts, then among the added ones; `set_chart`/`remove_chart` both rely on `_visible_generated` for that mapping. `TableView` sizes itself to its rows (`table_height`: border + header + rows, 4..20 lines, +1 line when a horizontal scrollbar appears). Because runs differ in what they logged, `ChartsScreen` decides per chart what THIS run has before fetching (`_in_this_run`, `_x_in_this_run`, built from `_metric_set`/`_system_set`): a plot draws its present series (absent ones keep their color slot and are named in the subtitle) and never requests the absent ones; a chart with nothing available (no series, missing x-axis metric, missing table/image key, all-missing bar values) calls `show_unavailable(message)` and collapses to `NOTE_HEIGHT`, and returns to full size when a refresh finds the data. Shared customizations that reference things a run lacks are harmless (`apply_customization` ignores unknown panels/keys). The screen's layout attribute is `chart_layout` because `Widget.layout` is a read-only Textual property.
- Ordering: runs are sorted server-side (`order="-heartbeat_at"`). Projects use one GraphQL query per page that also fetches each project's newest run, `runCount`, and active-run count (`runCount(filters: {"state": "running"})`) (`PROJECTS_ACTIVITY_GQL`, via the private `_service_api.execute_graphql`), sorted client-side by newest run heartbeat or creation time. If that query fails it falls back to SDK listing by creation time. The query's shape was not verified against the live schema, only against fields the SDK itself uses.
- Sorting the runs list (`runsort.py`, UI-free; `RunsScreen` + `SortDialog`, key `s`, clickable headers): the server delivers runs newest-activity-first and that stays the default ("activity"; `descending=True` means newest first). Other columns sort client-side from **raw values** stored in `Item.sort` (run time as seconds, not "2h 41m"; also saved in the list cache — rows cached before sorting existed lack it and fall back to their cells), with natural name order, blanks always last, and stable ties. `BrowseScreen` keeps `_items` in arrival order and re-draws via `display_order()`/`resort()`; a streaming list shows arrival order and is re-sorted once when complete. The choice persists via `Preferences` (`preferences.py`, `preferences.json` in the config dir, same version/tolerance rules as the chart layouts).
- **The SDK memoizes run listings:** `Api.runs()` keeps each listing (with the pages it already fetched) by path+filters+order, so a second call returns the same stale runs and a run started while the app is open never appears. `WandbApiClient.iter_runs` therefore drops the project's memoized listings first (`_forget_run_listings`); `tests/test_client.py` uses a fake that memoizes like the SDK. Anything else that lists W&B objects repeatedly needs the same care.
- **Loading from W&B is parallel where it can be.** `WandbApiClient._run` loads different runs at the same time (its lock only guards the dicts, never the network call; per-run gates make two threads asking for one run share one load: it used to hold one lock during the call, which serialised every run load). `CompareScreen` loads every run and every part of a run (details, metadata, system rows, the run's summary) on one pool capped at `LOAD_WORKERS` (8); `ChartsScreen._fetch_data` sends its three requests together; series batches (`SERIES_WORKERS` at once in a run, `LOAD_WORKERS` across runs in a comparison) are fetched concurrently and drawn in chart order as each arrives; bulk run actions use `BULK_WORKERS` (4). Not parallelisable: run/project listings (cursor pagination). Tests prove concurrency with `threading.Barrier`s, which only pass if the requests are in flight together. **Plot loading is batched and prioritised.** `metric_series_many(ref, names, x)` asks for several metrics in ONE request (the SDK's own `sampledHistory` query with one spec per metric; the SDK's public `history(keys=[...])` would merge the keys into one jointly-sampled spec and change the data, so the private `Run._exec` is used, falling back to one public `history` call per metric if that fails). `ChartsScreen._load_views` / `CompareScreen._load_plots` collect everything the panel's plots need and fetch it in batches of `SERIES_BATCH` (20), top chart first, drawing each plot as soon as all its series are in. The fetch workers are `exclusive` in their own group and `_show_panel` cancels the group first, so a panel that was left never queues work ahead of the one being looked at (a request already in flight cannot be aborted, later batches are skipped). `CachedClient` only requests the metrics it does not have. Never go back to one worker/request per chart.
- Run list "Run time" is derived from start and last heartbeat (until now if running), not W&B's own runtime summary metric, to avoid loading each run's summary.
- Caching (`api/cache.py`, `api/cached.py`, `~/.cache/wandb-cli-tool`, override with `WANDB_CLI_TOOL_CACHE_DIR`): (1) project/run lists use stale-while-revalidate in `BrowseScreen` (cached list shown at once, fresh list swapped in when complete, highlight preserved; `r` bypasses the cache). (2) `CachedClient` wraps the real client and caches chart data (metric keys, series, system rows) only for **finished** runs, keyed by run path plus heartbeat (`RunRef.version`, which is `None` for unfinished runs, so those are never cached). Logs are not cached. Logout wipes the cache.
- Run screen data: `run_details` (state/start/group/tags, never cached since tags change without the run changing), `run_metadata` (wandb-metadata.json parsed by `parse_metadata`; git "dirty" = a `diff.patch` file exists; cached for finished runs), `run_config` (cached for finished runs). Group/tag dropdowns are built from the groups/tags in the already-loaded run list (Tags column), so no project-wide scan. After an edit, `app.touched_projects` makes `RunsScreen` refresh in place on resume.
- Files: `FilesScreen` shows `run.files()` as a folder `Tree` split on `/` (`build_file_tree`/`populate_tree`; slashless names sit in the root, folders first, all collapsed initially). `FileScreen` downloads to `<cache>/files/<sha(path|name|md5)>/` (content-addressed, pruned at 500 MB, wiped on logout) and previews by `media.file_kind`: images via `textual-image` (zoom `+`/`-`/`0`, render mode `m` cycling auto/half-cell/unicode; previews capped at 50 MB), audio via an external player (`player.py`: mpv, ffplay, afplay, paplay, play, aplay; injectable as `WandbCliApp(audio_player=...)`; plays on the machine running the app, not through SSH), text (`.json`, `.txt`, any `text/*`; JSON is pretty-printed, capped at 5 MB / 20,000 lines) in a `RichLog`; anything else gets a placeholder. Footer keys that don't apply to the current file type must be hidden with `check_action` returning `False` (`None` only dims them). `safe_relative_path` guards download names against path traversal. `terminal.py` measures the terminal's cell size (window-size ioctl, else `CSI 16 t` with a 1 s timeout) in `main()` *before* Textual starts and injects it into `textual_image._terminal.get_cell_size._result`; without it the library guesses 10x20 px, sizes sixel images wrongly, and they spill past their area (a sixel running past the bottom makes xterm.js scroll). The image status line shows the detected renderer and cell size. **The widget for "auto" mode must be `textual_image.widget.Image`, never `AutoImage`**: on sixel terminals `Image` is a dedicated widget (with an inner `_ImageSixelImpl`) that injects sixel data into Textual's rendering, while `AutoImage` wraps the plain sixel renderer, which Textual drops, leaving a blank/dark area (headless tests can't see this because without a tty both resolve to the same class; `test_in_a_sixel_terminal_auto_mode_is_the_dedicated_sixel_widget` imports the module in a pty that claims sixel support). To debug what the app really writes to a terminal, run it under a pty that answers `ESC[c` with `ESC[?1;2;4c` and replay the captured bytes. For VS Code, `terminal.integrated.enableImages` and `gpuAcceleration` must be on (see README).
- Copy run (`c` in the run screen; `api/copy_run.py`, `screens/copy.py`): W&B has no copy API, so `copy_run()` replays the source into a NEW run through the logging SDK, against small `RunSource`/`RunSink` protocols so the logic is unit-tested without W&B (`tests/test_copy_run.py`); `WandbSource`/`WandbSink` are the thin real adapters and are only tested against mocks. It runs in a child process (`CopyJob`, `child_main`): the API key goes via the `WANDB_API_KEY` env var, never argv; progress is JSON lines prefixed with `@@wbt@@`; cancel = SIGINT (the child finishes the new run as failed), forced after a grace period. The new run is `"<name> (copy)"` in the same project, with a fresh random id (never pass `id`/`resume`/`fork_from`), and is created with stats/metadata/git/code logging disabled so it does not record the copying machine. Copied: config, tags, group, notes, job type, history rows (steps kept), summary extras, files (minus `config.yaml`/`wandb-summary.json`), user output artifacts re-uploaded. Linked, not duplicated: input artifacts. NOT copied: system metrics (no public API), original `_timestamp`/`_runtime` of rows, reference artifacts, W&B-internal artifacts (run_table, code, job, `wandb-*`). **Artifact safety guard:** an artifact is only re-logged if its rebuilt manifest digest equals the original's, so W&B de-duplicates it; otherwise it is skipped with a warning, because logging different content under the same name would add a version to the user's existing collection. The source run is only read. Not verified against a live W&B account.
- Rename (`r`) is `rename_run`: a minimal `upsertBucket` with `displayName` only.
- `screens/login.py` has `LoginScreen` (key, then a `Select` dropdown of entities from `viewer.entity` + `viewer.teams`, created only after the key validates) and the modal `EntityScreen`.

- Key bar: every screen yields `KeyBar` (`screens/keybar.py`, a `Footer` subclass that wraps onto up to 3 lines instead of scrolling sideways; "key label" pairs use non-breaking spaces so they wrap whole). It shows the active `show=True` bindings, so keep it short with `check_action`: return **False** to hide a key that does nothing right now (`ChartsScreen`: `x`/`o`/Delete only with a (plot) chart focused, `d` only when the layout is customized, `f` only while the run is live; `RunsScreen`: Compare needs 2 selected). Call `refresh_bindings()` whenever the answer can change. A hidden key is also inert, so there is no "focus a chart first" hint any more. **Every key that switches something must show what it is set to on the key bar**: the node owning the binding defines `toggle_state(action) -> bool | None` (on/off keys: shown as ☑/☐) and/or `key_label(action) -> str | None` (a key that cycles a value: shown as e.g. "Auto-refresh: 30 s"; also for a key whose label changes with state, like Play/Stop) and calls `refresh_bindings()` whenever that changes. Current ones: compare `i` (hide identical rows, per table), compare table `v`, logs `f`, charts `f`, file preview `m` and Space.
- Comparing runs (`compare.py` UI-free, `runfacts.py` the run's header facts shared with `RunScreen`, `screens/compare.py`, `screens/compare_widgets.py`): `RunsScreen` keeps `selected` (run ids in pick order; Space toggles, `c` opens `CompareScreen` for 2..`MAX_RUNS` = 8 = palette size runs, `u` clears). A run's color is its position in the selection (palette slot, never cycled). `CompareScreen` fetches every run in a thread pool (`fetch_run`: details, metadata, config, metric keys/values, system rows; a failing part is empty and reported) and has four tabs: Overview (`overview_rows`, `≠` marks differing rows), Metrics (see below), Config (`flatten_config` -> dotted paths, lists up to 20 items one entry each, then `diff_config`: only entries whose values differ or that only some runs have; identical ones are counted and shown with `d`), Charts (the project's saved layout via `apply_customization` over the UNION of all runs' metrics, read-only; `compare_charts` splits a multi-metric plot into one `ComparePlotView` per metric (small multiples, so runs x metrics never share one plot), a bar chart becomes one `CompareBarView` with a group of bars per metric and one bar per run; tables and images are compared too, see below). A plot whose runs all have exactly one point (`is_single_value`) is drawn as bars. Runs lacking a metric/x-axis are never queried and are named in the subtitle. Series are cached per (run, system, metric, x) for the screen. Everything is read-only.
- **Chart editing is shared:** `screens/chart_editing.py` (`ChartEditing` mixin: new panel, add/change/delete chart, x-axis, options, reset) is used by `ChartsScreen` AND `CompareScreen` (Charts tab: `n a x o Delete d`; the identical-rows toggle there is `i`). The screen supplies `chart_layout`, `selected`, `panels`, `metrics`/`system_metrics`/`tables`/`images` (the UNION over the compared runs in a comparison), `_layout_key`, `_focused_chart()`, `_refresh_panel_list()`, `_show_panel(focus)`, `_update_status()`. Chart indexes in the mixin are LAYOUT positions: `CompareChart.source`/`.index` say which layout chart a drawn chart came from (a multi-metric plot is drawn as several charts but is ONE layout chart, so x-axis/options/delete act on all of them). `CompareScreen.panels` is the layout's panels (empty panels included, so a new panel is visible).: `ymin`/`ymax`, `smooth` EMA weight 0-0.99, `logy`, `logx`; `ChartSpec.opts`; key `o` in `ChartsScreen` -> `ChartOptionsDialog`, `parse_options` validates): generated charts store overrides in `Customization.opts[panel][chart_key]` (like `x`), added charts carry them inside the spec. The stored format only gained optional fields, so `LAYOUT_VERSION` stays 2 and old files load. Smoothing/log filtering is `series.prepare_points` (`smooth_ema` is W&B's bias-corrected EMA; a log axis drops non-positive points and the subtitle says how many); widgets apply it in `show`, `chart_widgets.apply_axis_options` sets log scale and `ylim`. Compare charts honour the same options. A **bar** chart only uses `ymin`/`ymax` as the value axis (`layout_bars(low, high)`: the baseline is zero when zero is on the axis, otherwise the end nearest zero; values are clipped, the figure stays the real value).
- Run list extras (`RunsScreen`): `/` filter (every word must occur in the row's cells; `_add_row` skips non-matching rows so `resort()`/streaming stay consistent; Esc clears the filter first, then goes back), selection is unlimited (only *comparing* is capped at `MAX_RUNS`), `ctrl+a` selects all shown, `a` opens `RunActionsDialog` for the selection (or the cursor run): stop the running ones / set group / add tags / delete, applied one run after another by `_apply` with per-run failures reported. **Pins:** `p` pins runs (`Pins`, `pins.py`, per project in `Preferences`; `pinned_first` puts them first in `display_order` over whatever the sort is, ★ in the name cell). **Deleted runs:** `app.deleted_runs` holds runs deleted this session; `RunsScreen` drops them from the rows at once (`_drop_deleted`), from the cached list, and from every fetch, because W&B's listing can still return a deleted run for a while. **Watching:** every `WATCH_SECONDS` (30) while the list is the current screen and a run is running, `_watch_tick` refreshes in place; `_replace` compares old/new states and `_announce_changes` notifies (finished / failed / new run, beep on failures); a failed background check is silent. `o` opens the run in the browser (`client.run_url` = `Run.url`; the host is NOT always wandb.ai, so never build URLs by hand) through `app.open_link` (the `o` key on the run list and in a run). `browser.py` chooses the command itself (`$BROWSER`, then `open` / `start` / `xdg-open` only when there is a display) and starts it with stdin/stdout/stderr detached: **never use `webbrowser.open`**, it can start a text-mode browser inside the TUI's terminal. With no way to open a browser the link goes to the clipboard (OSC 52) and is shown.
- Logs: `LogsScreen(ref, name, live)`: a running run's log is followed (`FOLLOW_SECONDS` 5; `console_lines` always yields the whole log, so a reload skips the lines already shown), `f` toggles, `r` reloads everything.
- Compare tables/images/metrics: tables of the layout are merged by `merge_tables` into one `CompareTableView` (a Run column with the run's color; `v` = rows grouped by run / lined up by first column; 300 rows per run), images by `CompareImageView` (one shared slider over `union_steps`; each run shows `nearest_step`; downloads go through `screens/imagefetch.fetch_thumbnail`, which `ChartsScreen` uses too). In the Metrics and Config tabs `/` filters by key (`matches_filter`, one filter per tab) and `p` pins keys (`Pins`, kinds `metrics`/`config`; a pinned config key is always listed by `diff_config(pinned=...)`, a pinned row ignores the identical-rows toggle but not the filter). The Metrics tab (`metric_rows`) lists every metric's latest value per run and marks the best run. **Lower is better by default and nothing is guessed from names:** `b` flips the metric under the cursor, `B` flips all; the metrics where higher is better are saved per project in `Preferences` (`compare_higher_is_better`).
- Shared helpers (from the simplify pass): `jsonfile.py` (`read_versioned`, `atomic_write_json`) is the one tolerant versioned-JSON reader / atomic 0600 writer used by `Preferences`, `LayoutStore` and `DiskCache`. `api/models.py` has `is_inside` and `download_run_file` (path-checked download) for every file download. `DiskCache.prune_dir_sometimes` rate-limits directory pruning. Dialogs derive from `CancellableDialog` (Esc cancels; button id `ok` calls `_submit()`); `KeyPickerDialog` is the base of `TableDialog`/`ImageDialog`. `ChartsScreen._deliver` is the shared "fetch in a worker, then show or report quietly" path for series, tables and image steps, and independent series are fetched concurrently (`SERIES_WORKERS`).
- **UI text rules:** the interface does not explain itself. No remarks about how things work (layouts are always shared by every run of a project, so never say so), no key hints in labels, subtitles or status lines (the key bar shows the keys; a key that matters only sometimes appears there through `check_action`), no "(press x to …)". Status lines show facts (counts, states), not instructions. Warnings before destructive actions are the exception.
- `tests/test_text_safety.py` scans `screens/*.py` with the AST: a `Static`/`Label` or `Static.update` given a non-literal must use `plain(...)`, a Rich object, or `markup=False`.

## Testing

Tests use Textual's headless `Pilot` with `FakeClient` in `tests/conftest.py`, with no network. They run in parallel (`pytest-xdist`, `addopts = "-n auto"`), so every test must be independent: state goes through the autouse `config_dir`/cache fixtures (a temp dir per test), never through module globals or the real home directory; a few tests use real timers (watch/follow intervals), so keep their margins generous. Async tests rely on `pytest-asyncio` auto mode. After key presses that trigger a worker, call `await pilot.pause()` (twice) before asserting.

## Constraints

- **Writes to W&B are limited to these explicitly user-triggered actions** (run screen, and the run list's `a` menu for the selected runs): set a run's group (`g`), add tags (`t`, add-only, never removes), rename a run (`r`, display name only; the id never changes), copy a run (`c`, only after a yes/no confirmation; it creates a NEW run in the same project and never modifies or deletes the source), stop a run (`s`, only while running, after a yes/no confirmation: `Run.stop()`, the same graceful flag as the app's Stop button), and delete a run (`Delete`, only after typing the word "delete" in `DeleteRunsDialog`: `Run.delete(delete_artifacts=False)`; the run's artifacts are deleted too ONLY if the user ticks the "Also delete the artifacts" box, which changes the word to be typed to "delete artifacts": a second, separate agreement, never a default). Group/tags/rename send a minimal `upsertBucket` mutation containing only the id and that one field. Do NOT use `Run.update()`: it rewrites config/notes/description and the entire summary, which can clobber a live run's metrics. **Moving or copying a run to another project is deliberately not offered:** the public SDK has no move API (0.31.2), an undocumented GraphQL mutation must not be guessed against a user's data, and a replayed copy would lose system metrics and artifacts, so it is not a move. Never make a destructive action possible with a single key press. Do not add any other write without the user asking.
- Never read or print the user's API key.
