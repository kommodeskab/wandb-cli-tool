# Runs, Files, and W&B API Architecture

- Ordering: runs are sorted server-side (`order="-heartbeat_at"`). Projects use one GraphQL query per page that also fetches each project's newest run, `runCount`, and active-run count (`runCount(filters: {"state": "running"})`) (`PROJECTS_ACTIVITY_GQL`, via the private `_service_api.execute_graphql`), sorted client-side by newest run heartbeat or creation time. If that query fails it falls back to SDK listing by creation time. The query's shape was not verified against the live schema, only against fields the SDK itself uses.
- Sorting the runs list (`runsort.py`, UI-free; `RunsScreen` + `SortDialog`, key `s`, clickable headers): the server delivers runs newest-activity-first and that stays the default ("activity"; `descending=True` means newest first). Other columns sort client-side from **raw values** stored in `Item.sort` (run time as seconds, not "2h 41m"; also saved in the list cache — rows cached before sorting existed lack it and fall back to their cells), with natural name order, blanks always last, and stable ties. `BrowseScreen` keeps `_items` in arrival order and re-draws via `display_order()`/`resort()`; a streaming list shows arrival order and is re-sorted once when complete. The choice persists via `Preferences` (`preferences.py`, `preferences.json` in the config dir, same version/tolerance rules as the chart layouts).
- **The SDK memoizes run listings:** `Api.runs()` keeps each listing (with the pages it already fetched) by path+filters+order, so a second call returns the same stale runs and a run started while the app is open never appears. `WandbApiClient.iter_runs` therefore drops the project's memoized listings first (`_forget_run_listings`); `tests/test_client.py` uses a fake that memoizes like the SDK. Anything else that lists W&B objects repeatedly needs the same care.
- **Loading from W&B is parallel where it can be.** `WandbApiClient._run` loads different runs at the same time (its lock only guards the dicts, never the network call; per-run gates make two threads asking for one run share one load: it used to hold one lock during the call, which serialised every run load). `CompareScreen` loads every run and every part of a run (details, metadata, system rows, the run's summary) on one pool capped at `LOAD_WORKERS` (8); `ChartsScreen._fetch_data` sends its three requests together; series batches (`SERIES_WORKERS` at once in a run, `LOAD_WORKERS` across runs in a comparison) are fetched concurrently and drawn in chart order as each arrives; bulk run actions use `BULK_WORKERS` (4). Not parallelisable: run/project listings (cursor pagination). Tests prove concurrency with `threading.Barrier`s, which only pass if the requests are in flight together. **Plot loading is batched and prioritised.** `metric_series_many(ref, names, x)` asks for several metrics in ONE request (the SDK's own `sampledHistory` query with one spec per metric; the SDK's public `history(keys=[...])` would merge the keys into one jointly-sampled spec and change the data, so the private `Run._exec` is used, falling back to one public `history` call per metric if that fails). `ChartsScreen._load_views` / `CompareScreen._load_plots` collect everything the panel's plots need and fetch it in batches of `SERIES_BATCH` (20), top chart first, drawing each plot as soon as all its series are in. The fetch workers are `exclusive` in their own group and `_show_panel` cancels the group first, so a panel that was left never queues work ahead of the one being looked at (a request already in flight cannot be aborted, later batches are skipped). `CachedClient` only requests the metrics it does not have. Never go back to one worker/request per chart.
- Run list "Run time" is derived from start and last heartbeat (until now if running), not W&B's own runtime summary metric, to avoid loading each run's summary.
- Caching (`api/cache.py`, `api/cached.py`, `~/.cache/wandb-cli-tool`, override with `WANDB_CLI_TOOL_CACHE_DIR`): (1) project/run lists use stale-while-revalidate in `BrowseScreen` (cached list shown at once, fresh list swapped in when complete, highlight preserved; `r` bypasses the cache). (2) `CachedClient` wraps the real client and caches chart data (metric keys, series, system rows) only for **finished** runs, keyed by run path plus heartbeat (`RunRef.version`, which is `None` for unfinished runs, so those are never cached). Logs are not cached. Logout wipes the cache.
- Run screen data: `run_details` (state/start/group/tags, never cached since tags change without the run changing), `run_metadata` (wandb-metadata.json parsed by `parse_metadata`; git "dirty" = a `diff.patch` file exists; cached for finished runs), `run_config` (cached for finished runs). Group/tag dropdowns are built from the groups/tags in the already-loaded run list (Tags column), so no project-wide scan. After an edit, `app.touched_projects` makes `RunsScreen` refresh in place on resume.
- Run list extras (`RunsScreen`): `/` filter (every word must occur in the row's cells; `_add_row` skips non-matching rows so `resort()`/streaming stay consistent; Esc clears the filter first, then goes back), selection is unlimited (only *comparing* is capped at `MAX_RUNS`), `ctrl+a` selects all shown, `a` opens `RunActionsDialog` for the selection (or the cursor run): stop the running ones / set group / add tags / delete, applied one run after another by `_apply` with per-run failures reported. **Pins:** `p` pins projects on `ProjectsScreen` (`Pins(..., entity)`, kind `"projects"`, stored per entity in `Preferences`, `★` prefix, keeps cursor row) and runs on `RunsScreen` (`Pins`, `pins.py`, per project in `Preferences`; `pinned_first` puts them first in `display_order` over whatever the sort is, ★ in the name cell). **Deleted runs:** `app.deleted_runs` holds runs deleted this session; `RunsScreen` drops them from the rows at once (`_drop_deleted`), from the cached list, and from every fetch, because W&B's listing can still return a deleted run for a while. **Watching:** every `WATCH_SECONDS` (30) while the list is the current screen and a run is running, `_watch_tick` refreshes in place; `_replace` compares old/new states and `_announce_changes` notifies (finished / failed / new run, beep on failures); a failed background check is silent. `o` opens the run in the browser (`client.run_url` = `Run.url`; the host is NOT always wandb.ai, so never build URLs by hand) through `app.open_link` (the `o` key on the run list and in a run). `browser.py` chooses the command itself (`$BROWSER`, then `open` / `start` / `xdg-open` only when there is a display) and starts it with stdin/stdout/stderr detached: **never use `webbrowser.open`**, it can start a text-mode browser inside the TUI's terminal. With no way to open a browser the link goes to the clipboard (OSC 52) and is shown.
- Logs: `LogsScreen(ref, name, live)`: a running run's log is followed (`FOLLOW_SECONDS` 5; `console_lines` always yields the whole log, so a reload skips the lines already shown), `f` toggles, `r` reloads everything.
- Files: `FilesScreen` shows `run.files()` as a folder `Tree` split on `/` (`build_file_tree`/`populate_tree`; slashless names sit in the root, folders first, all collapsed initially). `FileScreen` downloads to `<cache>/files/<sha(path|name|md5)>/` (content-addressed, pruned at 500 MB, wiped on logout) and previews by `media.file_kind`: images via `textual-image` (zoom `+`/`-`/`0`, render mode `m` cycling auto/half-cell/unicode; previews capped at 50 MB), audio via an external player (`player.py`: mpv, ffplay, afplay, paplay, play, aplay; injectable as `WandbCliApp(audio_player=...)`; plays on the machine running the app, not through SSH), text (`.json`, `.txt`, any `text/*`; JSON is pretty-printed, capped at 5 MB / 20,000 lines) in a `RichLog`; anything else gets a placeholder. Footer keys that don't apply to the current file type must be hidden with `check_action` returning `False` (`None` only dims them). `safe_relative_path` guards download names against path traversal. `terminal.py` measures the terminal's cell size (window-size ioctl, else `CSI 16 t` with a 1 s timeout) in `main()` *before* Textual starts and injects it into `textual_image._terminal.get_cell_size._result`; without it the library guesses 10x20 px, sizes sixel images wrongly, and they spill past their area (a sixel running past the bottom makes xterm.js scroll). The image status line shows the detected renderer and cell size. **The widget for "auto" mode must be `textual_image.widget.Image`, never `AutoImage`**: on sixel terminals `Image` is a dedicated widget (with an inner `_ImageSixelImpl`) that injects sixel data into Textual's rendering, while `AutoImage` wraps the plain sixel renderer, which Textual drops, leaving a blank/dark area (headless tests can't see this because without a tty both resolve to the same class; `test_in_a_sixel_terminal_auto_mode_is_the_dedicated_sixel_widget` imports the module in a pty that claims sixel support). To debug what the app really writes to a terminal, run it under a pty that answers `ESC[c` with `ESC[?1;2;4c` and replay the captured bytes. For VS Code, `terminal.integrated.enableImages` and `gpuAcceleration` must be on (see README).
- Copy run (`c` in the run screen; `api/copy_run.py`, `screens/copy.py`): W&B has no copy API, so `copy_run()` replays the source into a NEW run through the logging SDK, against small `RunSource`/`RunSink` protocols so the logic is unit-tested without W&B (`tests/test_copy_run.py`); `WandbSource`/`WandbSink` are the thin real adapters and are only tested against mocks. It runs in a child process (`CopyJob`, `child_main`): the API key goes via the `WANDB_API_KEY` env var, never argv; progress is JSON lines prefixed with `@@wbt@@`; cancel = SIGINT (the child finishes the new run as failed), forced after a grace period. The new run is `"<name> (copy)"` in the same project, with a fresh random id (never pass `id`/`resume`/`fork_from`), and is created with stats/metadata/git/code logging disabled so it does not record the copying machine. Copied: config, tags, group, notes, job type, history rows (steps kept), summary extras, files (minus `config.yaml`/`wandb-summary.json`), user output artifacts re-uploaded. Linked, not duplicated: input artifacts. NOT copied: system metrics (no public API), original `_timestamp`/`_runtime` of rows, reference artifacts, W&B-internal artifacts (run_table, code, job, `wandb-*`). **Artifact safety guard:** an artifact is only re-logged if its rebuilt manifest digest equals the original's, so W&B de-duplicates it; otherwise it is skipped with a warning, because logging different content under the same name would add a version to the user's existing collection. The source run is only read. Not verified against a live W&B account.
- Rename (`r`) is `rename_run`: a minimal `upsertBucket` with `displayName` only.
